# Lua プラグインのセキュリティ境界

LuaJIT FFI を有効にしたコードは、実行ユーザーと同じ権限を持つネイティブプログラムとして扱います。[LuaJIT の FFI](https://luajit.org/ext_ffi.html) は C 関数やメモリへ直接アクセスできます。`os` / `io` を隠したり、`dxt.load_library` の名前を制限しても、直接の `ffi.C` / `ffi.load` で回避できるため、未信頼コードの隔離にはなりません。

## 確認した問題

- 変更前は、CLI の許可なしにジョブ YAML から Lua を実行できた。`check` でもトップレベルでファイルを作れることを、一時ディレクトリのマーカーで再現した。`open` / `open_writer` を呼ばないことは、無害な検証を意味しない。
- 標準ライブラリ・FFI からファイル、プロセス、環境変数、ネットワークへアクセスできる。ネイティブのメモリ破壊やプロセス終了も防げない。
- 従来の `require` のフォールバックは、`LUA_PATH` / `LUA_CPATH` 等から意図しない依存コードをロードする可能性があった。
- ソースとバイトコードを自動判別してロードし、スクリプトのサイズにも上限がなかった。
- Lua のヒープ、ネイティブの確保領域、実行時間は DataFusion の `--memory-limit` では制限されない。戻らないネイティブ関数は Lua の実行フックでも停止できない。
- `dxt.job` は同じジョブの全 Lua プラグインに共有される。異なる信頼主体の間の隔離や、秘密情報へのアクセス制御にはならない。

## 実装した対策

Lua は既定で無効です。Lua 入出力またはジョブ直下の `lua` を含む場合、評価する前に終了コード2で拒否します。信頼できるコードに限り、実行者が CLI で明示許可します。

```sh
dxt run --allow-lua trusted-job.yml
```

`check` / `explain` / `check --scan` にもこの指定が必要です。許可した場合、これらのコマンドでもトップレベルを評価します。YAML、`import`、環境変数から実行を自己許可する仕組みは設けません。ライブラリ利用時も `Job::allow_unsafe_lua()`、単独の定義には `Dataset::allow_unsafe_lua()` による明示許可が必要です。

標準ローダーはテキストのみを受け付け、メイン・フック・補助モジュールの各ファイルを1 MiBまでに制限します。補助モジュールはスクリプトのディレクトリ内だけを検索し、ディレクトリ外へ出る symlink を拒否します。標準モジュール・組み込み preload 以外について、`LUA_PATH` / `LUA_CPATH` / カレントディレクトリから暗黙にロードしません。組み込み `ffi` は同名のローカルファイルより優先します。

これらは意図しない実行や依存コードの取り違えを減らす対策です。`--allow-lua` は権限を制限するオプションではありません。許可したスクリプトが別のローダーや FFI を使うことは防ぎません。スクリプト、補助モジュール、共有ライブラリ、その依存物、配置ディレクトリ、実行環境全体を信頼できる場合だけ使用してください。直接パス指定も、依存ライブラリの安全性まで保証しません。

既定拒否、YAML による自己許可の拒否、ライブラリ API の拒否、バイトコード・過大ファイル・環境経由のモジュール検索・外部 symlink・組み込みモジュールの差し替えを回帰テストしています。

## 未信頼コードを扱う設計

未信頼 Lua をホストプロセス内で実行する機能は提供しません。FFI を維持して扱う場合は、ジョブごとの worker を別プロセスで実行し、OS の権限制限を組み合わせます。別プロセスに分けるだけでは、同じユーザーが読めるファイル等を保護できません。

1. 専用の低権限ユーザーを使用する。入力・コード・ライブラリは読み取り専用、専用作業領域だけを書き込み可能にする。ホーム、認証情報、SSH agent、管理ソケットを渡さない。
2. ネットワークは原則禁止し、必要なら実行基盤側で許可した DB 等だけに接続させる。DB の権限も対象テーブルと必要な操作に絞る。
3. メモリ・CPU・経過時間・プロセス数・出力サイズを監視側から制限する。期限超過やプロトコル違反では worker を停止し、未確定出力を破棄する。
4. ホストとの通信はスキーマとデータに限定し、メッセージ長・型・行数等を検証する。任意ファイル操作やコマンド実行を要求できる API は渡さない。
5. `dxt.job` とネイティブハンドルは同じ worker 内で保持する。プロセス間にポインターや cdata を渡さない。
6. 隔離ポリシーは実行者側が管理し、ジョブ YAML では緩和できないようにする。隔離できない環境では未信頼コードを拒否する。

コンテナを使う場合も、[名前空間・権限・マウントの制限](https://docs.docker.com/engine/security/)と[明示的な資源制限](https://docs.docker.com/engine/containers/resource_constraints/)が必要です。既定設定だけで十分な隔離や資源上限があるとは扱いません。より強い隔離が必要なら VM 等の分離も検討します。

worker と OS 隔離は今後の実装範囲です。現時点で利用できるのは「既定拒否」と「明示許可した信頼済みコードの実行」です。
