# 共通化と実行コストの改善

測定日: 2026-11-06。コードレビューで挙げた共通化・性能・可読性の改善を、変更前のreleaseバイナリと比較します。

## 変更内容

- `process` はSQLの計画時に名前付き参照として保持します。DataFusionの通常の `ViewTable` は参照先を早期展開するため、専用のテーブルプロバイダーで展開を遅らせます。依存順に各processの順序付き計画を一度だけ作り、参照時は不変の計画を別名の内側で再利用します。列をそのまま渡す射影も省略し、深い再帰と再計算を減らします。未使用processも検証します。
- `check` の評価用Arrow配列を参照列だけに絞り、診断文字列は必要時に生成します。CSV・物理形式では行のチェックと変換を同じループで処理し、CSVの書き込みバッファと物理形式の作業領域を再利用します。入力の全列検証、行順・ルール順、最初の変換エラーとログの優先順位を維持します。
- ICU日時・文字コード・バイト列操作・COBOL関数に、スカラーと配列を共通に参照する引数アクセサーを導入します。文字列・バイナリを借用し、定数引数を行数分の配列へ展開する処理をなくします。書式・文字コードのキャッシュを共通化し、呼び出しごとに最大128件に制限します。
- バイナリ出力はArrowから借用したバイト列を再利用バッファへ直接変換します。条件付き入力はNULL初期値と作業領域を再利用し、条件式の参照列だけをArrowへ変換します。条件結果に応じた項目選択を最大128通りまでキャッシュします。
- CSV・固定長の並列出力のチャネル、書き込みスレッド、CPUセマフォ、終了待ち、エラー回収を共通化します。出力形式ごとのwriter・encoder・bufferを列挙型の同じvariantへまとめます。
- シグナル待機の分岐を整形し、依存参照の収集と検証を名前付きの変数に分けます。

## 比較条件

`review_workloads.py` に変更前バイナリの比較、連鎖するprocess、バイナリ・条件付きレイアウト、SQL関数の測定を追加しました。実行順をシャッフルし、方式ごとにウォームアップ1回＋本測定3回、1/4スレッドで測ります。表はCLI全体の経過時間の中央値です。計画の測定には設定読込・物理計画の検証も含まれます。

データ処理は65,536行。16列のParquetはCSV換算16 MiB、100列は100 MiB、バイナリ・条件付き固定長は16 MiBです。入力のキャッシュを温め、同期・公開までを含めます。Parquetは未使用列を含む全列をデコードします。CPU時間・最大RSS・全試行・実行計画・バイナリのSHA-256は[生データ](results/review-improvements-65536.json)に保存します。

## 測定結果

4スレッドの本測定3回の中央値です。速度比は変更前の時間÷変更後の時間で、1未満は変更後の方が長いことを表します。

| ケース | 変更前 秒 | 変更後 秒 | 速度比 |
| --- | ---: | ---: | ---: |
| process連鎖 1,000段 | 1.9082 | 0.0585 | 32.60倍 |
| process連鎖 100段 | 0.0482 | 0.0167 | 2.89倍 |
| 独立process 1,000件 | 0.0733 | 0.0687 | 1.07倍 |
| 独立process 100件 | 0.0172 | 0.0189 | 0.91倍 |
| 16列・checkなし | 0.0587 | 0.0593 | 0.99倍 |
| 入力check 1件 | 0.1522 | 0.0917 | 1.66倍 |
| 入力check 3件 | 0.2354 | 0.1537 | 1.53倍 |
| 出力check 1件 | 0.2838 | 0.1390 | 2.04倍 |
| 出力check 3件 | 0.3474 | 0.1977 | 1.76倍 |
| icu_length | 0.0480 | 0.0506 | 0.95倍 |
| icu_to_char | 0.0594 | 0.0479 | 1.24倍 |
| bstring 1項目の固定長変換 | 0.0489 | 0.0490 | 1.00倍 |
| 条件付きbstringの固定長変換 | 0.0944 | 0.0671 | 1.41倍 |
| Parquet 100列から100列をCSV出力 | 0.3860 | 0.3975 | 0.97倍 |
| Parquet 100列から2列をCSV出力 | 0.1116 | 0.1249 | 0.89倍 |

1スレッドのprocess連鎖1,000段は **2.0168秒 → 0.0604秒（33.37倍）** でした。4スレッドの入力checkは処理時間を約35〜40%、出力checkは約43〜51%短縮しました。bstring単項目など、今回の小規模な測定で明確な短縮が出ていないケースもあります。

Parquetと独立processには[追加確認36試行](results/review-improvements-confirmation-65536.json)も行いました。各方式ウォームアップ1回＋本測定5回の中央値は、Parquetの2列選択が **0.1261秒 → 0.1254秒**、100列出力が **0.3831秒 → 0.3826秒** で、経過時間はほぼ同等でした。両ケースの物理計画も変更前後で一致しています。100列出力の最大RSS中央値は **199.0 MiB → 209.7 MiB** でした。

独立process 1,000件・1スレッドの追加確認は **0.0711秒 → 0.0737秒**、最大RSS中央値は **55.6 MiB → 58.4 MiB** でした。順序付き計画の保持には追加メモリが必要です。今回の独立processの測定では、経過時間とメモリに小さな増分が見られました。

主測定240試行と追加確認36試行のうち、出力を伴う200試行は独立生成した期待値のサイズ・SHA-256と一致し、残り76試行はcheckが出力を生成しないことを確認しました。全276試行で一時領域の清掃も確認しています。短い測定にはばらつきがあり、異なる文字コード・SQL・ストレージへ同じ倍率を適用することはできません。

## 再現

変更前のreleaseバイナリを `/tmp/dxtran-before-review` に保存してから実行します。

```sh
cargo build --release --locked --offline --bin dxt --example parquet_fixture -j3
python3 -B benchmarks/review_workloads.py --skip-build \
  --rows 65536 --threads 1 4 --process-counts 100 1000 \
  --warmups 1 --repeats 3 --compare-dxt /tmp/dxtran-before-review \
  --result benchmarks/results/review-improvements-65536.json
```

## 検証

```sh
cargo test --locked --offline -j3
cargo clippy --locked --offline -j3 --all-targets -- -D warnings
cargo fmt --all -- --check
```

全271テスト、Clippy、フォーマット検査が成功しました。追加の回帰テストは、1,000段のprocessの名前付き参照・繰り返し参照・順序・未使用processの検証、128通りを超える条件選択とキャッシュの入れ替え、バッチをまたぐチェックと変換エラーの順序を確認します。

追加確認は、同じコマンドに `--repeats 5` と、次の `--cases` を指定して実行できます。保存先は `review-improvements-confirmation-65536.json` とします。

```sh
--cases parquet_100_select_2_threads_4 before_parquet_100_select_2_threads_4 \
  parquet_100_select_100_threads_4 before_parquet_100_select_100_threads_4 \
  plan_independent_1000_threads_1 before_plan_independent_1000_threads_1
```
